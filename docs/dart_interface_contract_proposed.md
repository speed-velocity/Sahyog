## 2. Classes and Interfaces

### 2.1 `HrSample`

Heart rate sample model used by the simulator to represent a single reading.

| Field | Type | Description |
|---|---|---|
| `ts` | `DateTime` | UTC timestamp of the reading (timezone-aware) |
| `hr` | `int` | Heart rate in beats per minute |

**Constructor:** `HrSample({required DateTime ts, required int hr})`  
**Validates:** `hr` must be in range 20-250 (demo bounds per `thresholds.md`)  
**Error:** Throws `ArgumentError` if `hr` is outside valid range or `ts` is naive (not UTC-adjusted)

**Rationale:** This is the internal Dart representation of a heart-rate sample. It mirrors the backend `DetectorReading` shape but exists only in the Flutter simulator — the backend owns the Pydantic `DetectorReading` model.

**Example:**
```dart
final sample = HrSample(ts: DateTime.parse('2026-11-23T10:00:03Z'), hr: 78);
```

### 2.2 `HeartRateSource`

Enum indicating the source of a heart-rate reading. Used to label simulated readings as distinct from device readings.

| Value | Meaning |
|---|---|
| `device` | Reading from a connected wearable (not used in this prototype) |
| `simulated` | Reading generated by the Flutter simulator (the only value used in demo) |

**Constructor:** `HeartRateSource.value(String label)` — internal use, typically `HeartRateSource.simulated`

**Static constants:**
- `HeartRateSource.simulated` — the only source used in the prototype; readings carry `source: "SIMULATED"` in the API request

**Rationale:** Per `PRD.md` §100 and `SYSTEM_DESIGN.md` D1, all generated readings must carry a source marker such as `SIMULATED`. The Flutter app must never imply that a real wearable is connected.

---

### 2.3 `SimScenario`

Enum identifying which demo scenario to run. These are the three exact scenario identifiers approved by the team.

| Value | Description |
|---|---|
| `normal` | NORMAL — no anomaly, no incident, no verification, no escalation |
| `trueAnomaly` | TRUE_ANOMALY — sustained abnormal pattern; detection → verification → escalation |
| `falseAlarm` | FALSE_ALARM — same abnormal pattern triggers detection, but user confirms `I_AM_OK` → `RESOLVED_FALSE_ALARM` |

**Constructor:** `SimScenario.value(String identifier)` — internal use  
**String values:** `'NORMAL'`, `'TRUE_ANOMALY'`, `'FALSE_ALARM'` — these are the exact strings sent to the backend `POST /api/v1/demo/runs`

**Rationale:** Per `SYSTEM_DESIGN.md` §4.1 and `PRD.md` §133, the three scenario identifiers are exactly `NORMAL`, `TRUE_ANOMALY`, `FALSE_ALARM`. The same pipeline is used for all three; they differ in input data and expected outcome, not in underlying implementation.

**Important:** `TRUE_ANOMALY` and `FALSE_ALARM` use the same abnormal reading pattern. The distinction is the demo scenario and subsequent verification outcome. The readings can be identical — what changes is the user's verification response.

### 2.4 `SimulatorHeartRateSource`

Simulated heart-rate source that generates deterministic reading sequences per scenario. This is the Flutter-side simulator — it does not perform anomaly detection.

**Constructor:** `SimulatorHeartRateSource({required SimScenario scenario, required int sampleRateBpm})`
- `scenario`: the demo scenario to generate
- `sampleRateBpm`: approximate sampling interval in BPM (readings per minute); the actual interval is derived from scenario vectors in `anomaly_vectors.json`

**Public fields:**
- `simScenario`: `SimScenario` — the selected scenario
- `samples`: `List<HrSample>` — the generated sequence of samples (read-only after generation)
- `sampleIntervalMs`: `int` — milliseconds between samples, calculated from the scenario vector timing
- `isRunning`: `bool` — whether the simulator is actively generating readings
- `demoRunId`: `String?` — the backend-assigned demo run ID, once a scenario is started

**Methods:**
- `generateSamples()`: `List<HrSample>` — generates the deterministic sample sequence for the selected scenario. Uses the vectors from `docs/anomaly_vectors.json` as the source of truth. Returns a fresh list each call (idempotent, no internal mutable state).
- `start()`: `Future<String>` — starts the simulator, generates the first reading, and returns a `demo_run_id` from `POST /api/v1/demo/runs`. Throws if a scenario is already running.
- `stop()`: `Future<void>` — stops the simulator, calls `POST /api/v1/demo/runs/{demo_run_id}/reset` to cancel pending escalation, and clears internal state.
- `nextReading()`: `Future<HrSample?>` — generates and returns the next reading in the sequence, submitting it via `POST /api/v1/readings`. Returns `null` when the sequence is complete.

**Lifecycle rules:**
- Start and stop are safe to call multiple times; no duplicate active timers or streams are created.
- The simulator is restartable after stopping; a new `demo_run_id` is generated for each start.
- Scenario cannot be changed while running — calling `start()` with a different scenario while one is already running throws `StateError`.
- After stopping, the simulator can be started again with any scenario (restartable).
- `generateSamples()` is deterministic and reproducible — given the same `SimScenario`, the same sequence of `HrSample` values is produced every time.

**Error and lifecycle behavior:**
- `start()` throws `StateError` if a scenario is already running.
- `stop()` is a no-op if no scenario is running.
- `nextReading()` returns `null` when the generated sequence is exhausted.
- Scenario cannot be changed while running; must `stop()` first, then `start()` with the new scenario.
- If `nextReading()` is called when `isRunning` is `false`, it throws `StateError`.

**Unit tests and expected outputs:**
- `generateSamples(SimScenario.normal)` produces ~30 normal readings (65-75 bpm), deterministic offsets from `anomaly_vectors.json`.
- `generateSamples(SimScenario.trueAnomaly)` produces ~40 readings: start normal, then sustained abnormal pattern (88+ bpm spike or 57- bpm drop per thresholds.md).
- `generateSamples(SimScenario.falseAlarm)` produces the same abnormal pattern as `trueAnomaly`, but the scenario is designed for user confirmation.
- `start()` → `nextReading()` → `stop()` → `start()` produces a new unique `demo_run_id`.
- No duplicate active timers or streams are created across start/stop cycles.

### 2.5 `AnomalyEvent`

Event model representing a backend-detected anomaly. Flutter does not create `AnomalyEvent` instances through local detection — they are received as part of the backend reading response.

| Field | Type | Description |
|---|---|---|
| `eventId` | `String` | Backend-assigned event ID |
| `detectedAt` | `DateTime` | UTC timestamp of detection |
| `kind` | `String` | Internal kind: `"spike"` or `"drop"` (mapped to `HR_SPIKE`/`HR_DROP` by backend) |
| `firstAbnormalAt` | `DateTime` | First abnormal sample time for the event window |
| `lastHr` | `int` | Heart rate at the last abnormal sample |
| `durationMs` | `int` | How long the abnormal pattern persisted |

**Rationale:** Per `detector_integration_contract.md` §8 and §13, the reading response `detection_status` is `"ANOMALY_DETECTED"` when the backend detector emits an anomaly event. Flutter receives this status in the reading response and can construct a local `AnomalyEvent` for display purposes, but the event is purely informational — the backend-owned incident lifecycle is not affected by Flutter's interpretation.

**Flutter does not independently decide** whether an anomaly occurred. The `detection_status: "ANOMALY_DETECTED"` field in the `POST /api/v1/readings` response is the authoritative trigger.

### 2.6 `AnomalyDetector`

**Ownership decision:** This abstraction is defined strictly as a **backend-result adapter**, with no local threshold logic. It does not implement a competing detector.

**Why omit local detection:** Per `SYSTEM_DESIGN.md` D3 — "Backend-authoritative anomaly decision": The mobile application may contain interfaces, buffers or preview logic where required by the existing architecture, but it must not independently create a competing incident decision. Per `detector_integration_contract.md` §13: `ANOMALY_DETECTED` in the reading response is not by itself proof of a persisted incident status.

**Two options proposed for Aditya's approval:**

**Option A — Omit local anomaly detection entirely:**
- `AnomalyDetector` is not included in the Flutter codebase.
- Flutter uses `detection_status` from the backend reading response to determine if an anomaly was detected.
- `AnomalyEvent` is constructed locally only for display, based on backend data.
- No threshold, no local persistence, no local state.

**Option B — Define `AnomalyDetector` as a backend-result adapter only:**
- `AnomalyDetector` is included as a thin adapter that wraps the backend response model.
- It has no public `detect()` method that performs threshold comparison.
- Its purpose is to map backend `detector_result` / `anomaly_kind` values to the local `AnomalyEvent` model for readability.
- It explicitly documents that the backend is authoritative and local use does not trigger incident creation.

**Recommended:** Option A — omit local anomaly detection from Flutter and use `AnomalyEvent`/`backend response model` instead. This avoids the ownership conflict and keeps the implementation simple and correct per the approved architecture.

If Option B is preferred, the adapter would have:
- **Constructor:** `AnomalyDetector({required String detectorVersion})` — `detectorVersion` defaults to `"sahyog-hr-threshold-v1"`.
- **Fields:** `detectorVersion`, optional `baselineMean`, `baselineStd`.
- **Methods:** 
  - `AnomalyEvent? mapResult(Map<String, dynamic> backendResult)` — maps backend reading response to `AnomalyEvent` for display; returns `null` if `detection_status` is not `"ANOMALY_DETECTED"`.
  - `String? getKind(String detectionKind)` — maps internal kind `"spike"`/`"drop"` to human-readable form.
- **Error behavior:** `mapResult` raises if the backend result has unexpected structure.

### 2.7 `ReplyClassifier`

Classifies the person's verification response. Handles positive, negative and unrecognised phrases without sending unsupported backend actions.

**Constructor:** `ReplyClassifier()` — no parameters required.

**Methods:**
- `ReplyResult classify(String reply)` — classifies the person's response string.

**Returns:** `ReplyResult` enum with values:
- `ok` — person confirms they are okay (approved phrases: `I'm okay`, `I am okay`, `I'm fine`, `I'm safe` and close variants)
- `notOk` — person indicates they are not okay (approved phrases: `I'm not okay`, `I need help`, `Help me`, `No, I need help.`)
- `unrecognised` — empty, whitespace-only, unrelated, or incomplete text

**Classification rules (per `detector_integration_contract.md` §12):**
- Normalize Unicode NFKC, case, surrounding whitespace, punctuation, and apostrophe variants.
- Check negative safety phrases before positive phrases.
- Use phrase/token boundaries; do not classify substrings such as `helpful` or `notokay` as approved phrases.
- Return `unrecognised` for empty, whitespace-only, unrelated, or incomplete text.
- **Critical invariant:** `I'm not okay` must never classify as `ok`.

**Approved positive phrases:**
- `I'm okay`
- `I am okay`
- `I'm fine`
- `I'm safe`
- Close variants: `I'm OK`, `I am safe` (must be kept aligned with Flutter)

**Approved negative phrases:**
- `I'm not okay`
- `I need help`
- `Help me`
- `No, I need help.`

**Error behavior:**
- Raises `ArgumentError` if `reply` is `null`.
- `unrecognised` is returned for any text that does not match approved positive or negative phrases at token boundaries.

**Unit tests and expected outputs:**
- `classify("I'm okay")` → `ReplyResult.ok`
- `classify("I am okay")` → `ReplyResult.ok`
- `classify("I'm fine")` → `ReplyResult.ok`
- `classify("I'm safe")` → `ReplyResult.ok`
- `classify("I'm not okay")` → `ReplyResult.notOk`
- `classify("I need help")` → `ReplyResult.notOk`
- `classify("Help me")` → `ReplyResult.notOk`
- `classify("I'm OK")` → `ReplyResult.ok` (close variant)
- `classify("I am safe")` → `ReplyResult.ok` (close variant)
- `classify("")` → `ReplyResult.unrecognised`
- `classify("   ")` → `ReplyResult.unrecognised`
- `classify("helpful")` → `ReplyResult.unrecognised` (substring, not token boundary)
- `classify("notokay")` → `ReplyResult.unrecognised` (no token boundary)
- `classify(null)` → throws `ArgumentError`

### 2.8 `LastMomentsBuffer`

Bounded rolling buffer of recent heart-rate samples. The current demo's evidence remains transient in memory — no database table, migration, or persistence layer.

**Constructor:** `LastMomentsBuffer({int maxSamples = 60, int maxMs = 30000})`
- `maxSamples`: maximum number of samples retained (default 60).
- `maxMs`: maximum retention window in milliseconds (default 30,000 / 30 seconds).

**Public methods:**
- `add(HrSample sample)`: `void` — adds a sample to the buffer. Rejects duplicates and out-of-order timestamps; counts rejections internally.
- `recent([int limit])`: `List<HrSample>` — returns up to `limit` recent samples in chronological order. Defaults to `maxSamples`.
- `window(DateTime start, DateTime end)`: `HrBufferSnapshot` — returns snapshot of samples whose timestamps fall within `[start, end]`, inclusive.
- `snapshot()`: `HrBufferSnapshot` — returns first/last time, min/max bpm, and rejection count.
- `reset()`: `void` — clears samples and rejection count.

**Rules:**
- Duplicate and out-of-order timestamps are rejected; rejection count increments.
- Accepted samples are normalized to UTC and ordered chronologically.
- Buffer remains bounded by `maxSamples`; older samples are pruned when the limit is exceeded.
- `reset()` clears all samples and the rejection count.
- No IDs, no persistence, no unbounded storage — purely in-memory.
- One buffer belongs to one backend lifecycle context. The backend must create a new buffer or call `reset()` when the subject/demo-run/generation changes.

**Rationale:** Per `detector_integration_contract.md` §11.2, the `LastMomentsBuffer` is a separate, bounded, in-memory recent-reading buffer. It is distinct from the core detector's evidence (which is abnormal-only and event-scoped). The buffer cannot supply normal readings or a pre-incident monitoring window from the core detector's evidence alone.

**Why a Flutter-side buffer may not be needed:** The backend already owns its detector evidence (bounded to 32 samples). If the Flutter UI only needs to display the most recent readings for context, the buffer can be optional — the backend can supply recent readings on demand via the dashboard API. However, if a local buffer is desired for UI preview purposes, the above specification provides a bounded, resettable implementation.

**Unit tests and expected outputs:**
- `LastMomentsBuffer()` with defaults creates a buffer with `maxSamples=60`, `maxMs=30000`.
- `add(HrSample(ts: DateTime.parse('2026-11-23T10:00:03Z'), hr: 78))` adds a sample; `recent()` returns it.
- Adding a duplicate timestamp increments rejection count but does not add a duplicate sample.
- Adding a timestamp earlier than the latest rejected sample increments rejection count and is not added.
- `snapshot().firstHr` and `snapshot().lastHr` return the correct min/max.
- `reset()` clears all samples and resets rejection count to 0.
- Buffer remains bounded: adding more than `maxSamples` prunes oldest samples.
- `maxMs` retention: samples outside the window are rejected on `add()`.

### 3.1 The AnomalyDetector Ownership Question

**Conflict:** The TEAM ownership list mentions `AnomalyDetector`, but Aditya explicitly requires Flutter to consume backend detection results rather than independently decide whether an anomaly occurred.

**Proposed resolution:** Define `AnomalyDetector` strictly as a **backend-result adapter** with no local threshold logic. Two options:

**Option A (Recommended):** Omit local anomaly detection from Flutter entirely. Use `AnomalyEvent`/`backend response model` instead. Flutter reads `detection_status` from the `POST /api/v1/readings` response and acts accordingly. No local detector is created.

**Option B:** Define `AnomalyDetector` as a backend-result adapter abstraction, with no local threshold logic. It maps backend `detector_result`/`anomaly_kind` to local `AnomalyEvent` for display purposes only. It explicitly documents that the backend is authoritative and local use does not trigger incident creation.

**Do not silently choose a competing detector implementation.** The contract must reflect that the backend Python anomaly service is the sole decision-maker for incident-creating anomaly events.

## 4. Reading Submission Flow (Full)

The complete flow for all three scenarios:

```
1. Flutter start scenario
   → POST /api/v1/demo/runs({scenario: SimScenario})
   ← returns demo_run_id

2. For each reading in the scenario sequence:
   → HrSample generated by SimulatorHeartRateSource
   → POST /api/v1/readings({
       demo_run_id,
       source: "SIMULATED",
       timestamp: sample.ts.toIso8601String(),
       heart_rate_bpm: sample.hr,
       activity: "RESTING",
     })
   ← returns {reading_id, demo_run_id, accepted, detection_status}
   
   - If detection_status == "NORMAL": continue to next reading
   - If detection_status == "ANOMALY_DETECTED": proceed to verification

3. If ANOMALY_DETECTED:
   → Show verification prompt: "Are you okay?"
   → Read person's reply through ReplyClassifier
   - If ReplyResult.ok: POST /api/v1/incidents/{incident_id}/verification({response: "I_AM_OK"})
   - If ReplyResult.notOk: handle appropriately (backend may initiate escalation)
   - If ReplyResult.unrecognised: retry prompt or handle timeout

4. Scenario completion:
   - NORMAL: no incident created, scenario can be reset or a new one started
   - TRUE_ANOMALY: verification times out → escalation → incident appears as "ESCALATED"
   - FALSE_ALARM: user confirms "I'm okay" → pending escalation cancelled → incident resolved as "RESOLVED_FALSE_ALARM"
```
